# Blockchain verification layer

## What this does

1. Take one flaring-data record (from `data/processed_flaring_data.json`,
   or any single JSON object).
2. Hash it with SHA-256 over a **canonical** (sorted-key) JSON form, so
   the hash is deterministic regardless of how the record was formatted
   or which order its fields were written in.
3. Send that 32-byte hash as the raw `data` field of a zero-value
   transaction on the **Polygon Amoy testnet**, from a wallet to itself.
4. Later, re-hash the record you currently have and compare it against
   what's actually stored in that transaction on-chain. Match = the data
   is exactly what was anchored; mismatch = it's been altered (or you've
   got the wrong tx) since anchoring.

## Why a plain transaction, not a smart contract

The task allowed either. This defaults to the plain-transaction approach:

- **Fewer moving parts.** A contract needs Solidity, a compiler, a
  deployment step, an ABI, and something to hold its deployed address.
  That's four more things that can silently break in a demo environment,
  for a competition submission judged on the concept, not contract
  engineering.
- **Same core guarantee.** For "prove this exact data existed at this
  exact time, immutably and publicly," a plain transaction gives you
  that already: the chain's own consensus timestamp on the confirming
  block is the anchor timestamp, and the transaction's `data` field is
  permanent and publicly readable — on PolygonScan, no contract ABI or
  "read" call needed, just the transaction page.
- **What you'd give up.** A contract could enforce things a plain tx
  can't: reject anchoring the same hash twice, emit an indexable event
  for building a dashboard of all anchors, or batch multiple hashes into
  one call (e.g. a Merkle root of many records) to save gas. None of
  that is needed to demonstrate the core idea, so it's noted here as a
  natural next step rather than built now.

## Files

- `scripts/lib/canonicalHash.js` — deterministic hashing (shared by both scripts)
- `scripts/lib/loadRecord.js` — shared CLI arg parsing / record loading
- `scripts/generate_wallet.js` — makes a throwaway testnet wallet (no network needed)
- `scripts/anchor_record.js` — anchors one record on-chain
- `scripts/verify_record.js` — re-hashes and checks a record against an on-chain anchor

## Setup

```
cd flarechain
npm install
cp .env.example .env
npm run generate-wallet        # prints an address + private key
# paste the private key into .env as PRIVATE_KEY=...
# fund the printed address at https://faucet.polygon.technology/ (select Amoy)
```

## Running it

Anchor a record (from the real dataset once you've generated it, or any
single JSON object for testing):

```
node scripts/anchor_record.js --file data/processed_flaring_data.json --index 0
```

This prints the computed hash, the transaction hash, the block number and
timestamp, and a PolygonScan link. It also appends an entry to
`data/anchors.json` — a **local convenience index only**, not part of the
trust model; it just saves you from having to remember which tx hash goes
with which record.

Verify a record against that anchor:

```
node scripts/verify_record.js --file data/processed_flaring_data.json --index 0 --tx 0xTHE_TX_HASH_FROM_ABOVE
```

(`--tx` can be omitted if the record's hash is still in `data/anchors.json`
— the script will look it up there. Either way, the actual comparison is
always done against a fresh read of the transaction from the chain, never
against the local file.)

To see tamper detection in action: edit one field in a copy of the record
(e.g. change `flared_volume_bcm`), run `verify_record.js` against the same
`--tx`, and it will print `MISMATCH` and exit with a non-zero status code.

## Why this hasn't been run end-to-end yet

Two real blockers, stated plainly rather than glossed over:

1. **No real record exists yet.** `data/processed_flaring_data.json` is
   generated by the Batch 1 Python scripts, which haven't been run
   against real downloaded World Bank data yet (see `docs/data_sources.md`).
2. **This sandbox can't reach Polygon.** Both the Amoy RPC endpoint
   (`rpc-amoy.polygon.technology`) and `amoy.polygonscan.com` are blocked
   by this environment's network egress policy — confirmed by direct
   `curl` tests, which timed out. Wallet generation and hashing were
   still tested locally (see the walkthrough below), since those need no
   network access; the on-chain anchor/verify calls have not been.

Everything above has been checked for correctness as far as this
environment allows:
- `npm install` succeeded, all five scripts pass `node --check`.
- The canonical hash function was tested directly: identical data in a
  different key order produces the identical hash; changing one field
  changes the hash.
- Both scripts' error-handling paths (missing `.env`, missing dataset
  file) were exercised directly and produce the intended clear messages
  and non-zero exit codes, rather than crashing.

**To actually get a real transaction hash and PolygonScan link**, run the
setup and anchor/verify commands above yourself (from a machine with
normal internet access), or hand me one real record plus a funded testnet
wallet in a session that can reach `polygon.technology`/`polygonscan.com`.
